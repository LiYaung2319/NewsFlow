# Web Source Parser

## Purpose

把“提供网址和采集需求，基于真实内容开发信息源解析器”落实为一个有确认闸门的工程流程。
先确认实际网页结构和数据，再写代码，避免将导航、广告、推荐内容或错误接口当成目标数据。

## Required Input

从用户请求中识别：

- 信息源标识；
- 信息源类型：`普通信息源` 或 `复合信息源`；
- 主网址以及用户提供的子页面或 API；
- 目标板块、字段、排序和条数限制；
- 是否需要去重、独立返回、独立格式化；
- 是否需要更新文档、测试、提交或推送。

如果用户没有说明普通或复合信息源，先询问并暂停，不要自行判断。

## Mandatory State Machine

严格按照以下状态执行：

```text
INIT
  -> READ_PROJECT
  -> DISCOVER_SOURCE
  -> PREVIEW_RESULT
  -> WAIT_PREVIEW_CONFIRMATION
       -> confirmed: DESIGN -> IMPLEMENT -> VERIFY -> PREPARE_COMMIT
       -> rejected/corrected: DISCOVER_SOURCE
  -> WAIT_COMMIT_CONFIRMATION
       -> confirmed: COMMIT
       -> otherwise: STOP
  -> WAIT_PUSH_CONFIRMATION
       -> confirmed: PUSH
       -> otherwise: STOP
```

### Hard gates

1. 在用户明确确认试采集结果前，不得修改业务代码、注册信息源或实现解析器。
2. 用户否定、补充或修正试采集结果时，必须回到 `DISCOVER_SOURCE`，重新访问并完整展示结果。
3. “看起来可以”“大概正确”等模糊回复不算确认，应继续询问。
4. 生成提交日志和文件清单后，必须等待用户明确确认，才可执行 `git add` 或 `git commit`。
5. 提交完成后必须再次等待用户明确确认，才可执行 `git push`。
6. 未得到对应确认时，只能报告当前状态，不得通过脚本、别名或自动流程绕过闸门。

## Read The Project First

在探查网站前读取当前项目的：

- 目录结构、入口和依赖；
- 数据模型；
- 解析器基类和已有解析器；
- 信息源注册表；
- HTTP/浏览器客户端；
- 采集编排、并发和错误处理；
- 格式化器及其来源标题映射；
- 测试、README 和 Git 提交习惯。

优先复用项目既有抽象。不要因为一个新网站而引入第二套采集或注册机制。

## Discover The Real Source

根据项目能力选择访问方式：

1. 优先使用项目已有的浏览器或 HTTP 客户端；
2. 动态页面使用 Playwright 或项目已有浏览器封装；
3. 监听或检查网络请求，识别页面实际使用的 JSON API；
4. 使用结构化 HTML、JSON 或 RSS 解析，不用脆弱的字符串截取；
5. 记录实际 URL、状态、等待条件、容器、字段和排序；
6. 区分目标内容与导航、广告、用户信息、项目卡片、历史内容及推荐内容；
7. 页面与接口不一致时，明确报告差异，不要猜测。

如果网站不可访问、需要登录、触发验证码或结构不足以确认需求，停留在探查阶段并说明阻塞原因。

## Preview Before Coding

试采集结果必须在修改代码前展示。按板块分组，每条至少显示标题和 URL，并说明：

- 访问的页面或接口；
- 实际采集方式；
- 每个板块采集数量与用户要求的差异；
- 是否有重复、混入或内容不一致；
- 当前无法确认的部分。

结尾使用明确的确认问题：

```text
以上试采集结果是否符合你的需求？
请明确回复“确认”或提供需要调整的内容。
在得到确认前，我不会修改业务代码，也不会实现解析器。
```

用户否定或修改后，重新完成完整探查和试采集展示，不要只描述改动方向。

## Source Type Branches

### Ordinary source

一个页面或接口对应一个解析器和一个结果键：

```text
source -> URL/API -> parser -> result key
```

只实现用户要求的单一采集逻辑，按需求截断条数并去重。

### Composite source

一个逻辑信息源包含多个需要独立返回的板块：

```text
source
├── section_a -> URL/API -> parser -> result_a
├── section_b -> URL/API -> parser -> result_b
└── section_c -> URL/API -> parser -> result_c
```

每个板块必须独立拥有页面/API、解析器实例、结果键、`source` 字段、数量限制和错误记录。
不要先合并成一个列表再用标题或位置推断来源。用户要求独立返回时，格式化也应生成独立消息。

## Implement

实现必须遵循当前项目的代码风格和边界：

- 继承既有解析器基类；
- 返回项目统一的数据模型；
- 标题和 URL 非空校验；
- URL 规范化和按 URL 去重；
- 使用 JSON 解析 API 响应；
- 不把当前采集到的标题、URL 或数量内容硬编码；
- 详情解析接口如项目已有约定则保留；
- 复合信息源分别注册 sections 或项目等价结构；
- 只有实际需要时才修改采集编排、formatter、模型和 README；
- 不做无关重构。

实现阶段开始前，应先简短说明拟修改的文件和板块映射。

## Verify

至少执行与项目匹配的以下检查：

```text
[ ] 解析器可导入或实例化
[ ] 信息源注册表包含目标标识
[ ] 普通/复合类型与用户输入一致
[ ] 结果键和 source 字段正确
[ ] 复合板块未合并
[ ] 数量限制正确
[ ] 标题、URL 非空且 URL 无重复
[ ] 真实网站链路验证通过
[ ] formatter 标题和消息边界正确
[ ] 语法检查通过
[ ] git diff --check 通过
```

优先用项目自己的客户端跑真实页面；不能访问时说明未完成真实验证及原因。没有自动化测试时要明确报告。

## Commit And Push Gates

用户要求提交或推送时，先检查分支、远程、工作区和相对远程的差异，只选择本次修改文件。
日志和文件清单必须先展示：

```text
拟提交日志：

标题：<单行标题>

正文：
- <变更一>
- <变更二>

拟提交文件：
- <path>

不提交文件：
- <运行产物或无关文件>

请核对以上提交日志和文件清单。
确认后我才会执行 git add、git commit。
```

### Commit text rules

- 标题单行、简洁并符合项目历史风格；
- 正文每条使用真实换行；
- 不得出现字面量 `` `n ``、乱码、调试输出或错误的标题正文混排；
- 不写令牌、密码、Webhook 或其它敏感信息；
- 提交前用 `git show --format=fuller --stat HEAD` 检查作者、日期、标题和正文；
- 用户要求作者和作者日期时，显式设置并核对 `Author`、`AuthorDate`；
- 不修改用户未授权的文件。

提交完成后仅展示提交哈希、作者、作者日期、文件和远程状态，并再次询问是否推送到目标分支。

## Security

不要要求用户在聊天中粘贴访问令牌。优先使用 SSH、Git Credential Manager、已登录 CLI 或外部凭据存储。
若用户已经提供令牌：只作为临时进程凭据使用，不写入文件、Git 配置、远程 URL、日志或提交正文，最终不重复展示，并建议推送后撤销和重新生成。

## Final Report

最终报告包含：修改文件、信息源标识、普通/复合类型、各板块结果键、采集方式、验证结果、未完成项和已知风险。
不要声称已提交或推送，除非相应命令实际成功且已核对远程状态。

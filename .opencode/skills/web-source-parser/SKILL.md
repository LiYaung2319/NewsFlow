# Web Source Parser

## Purpose

把“提供网址和采集需求，基于真实内容开发信息源解析器”落实为一个有确认闸门的工程流程。
先确认实际网页结构和数据，再写代码，避免将导航、广告、推荐内容或错误接口当成目标数据。

## Required Input

从用户请求中识别：

- 信息源标识；
- 信息源类型：`普通信息源` 或 `复合信息源`；
- 主网址以及用户提供的子页面或 API；
- 目标板块、字段、排序和条数限制；
- 是否需要去重、独立返回、独立格式化；
- 是否需要更新文档和测试。

如果用户没有说明普通或复合信息源，先询问并暂停，不要自行判断。

## Mandatory State Machine

严格按照以下状态执行：

```text
INIT
  -> READ_PROJECT
  -> DISCOVER_SOURCE
  -> PREVIEW_RESULT
  -> WAIT_PREVIEW_CONFIRMATION
       -> confirmed: DESIGN -> IMPLEMENT -> VERIFY -> FINAL_REPORT
       -> rejected/corrected: DISCOVER_SOURCE
```

### Hard gates

1. 在用户明确确认试采集结果前，不得修改业务代码、注册信息源或实现解析器。
2. 用户否定、补充或修正试采集结果时，必须回到 `DISCOVER_SOURCE`，重新访问并完整展示结果。
3. “看起来可以”“大概正确”等模糊回复不算确认，应继续询问。
4. 实现和验证完成后必须生成最终汇报，准确列出本次操作、代码文件及影响、验证证据、未完成项和已知风险。
5. 本 Skill 的职责到最终汇报结束，不生成版本控制提交日志，不读取提交作者或远端配置，也不执行提交或推送。

## Read The Project First

在探查网站前读取当前项目的：

- 目录结构、入口和依赖；
- 数据模型；
- 解析器基类和已有解析器；
- 信息源注册表；
- HTTP/浏览器客户端；
- 采集编排、并发和错误处理；
- 格式化器及其来源标题映射；
- 测试和 README 维护方式。

优先复用项目既有抽象。不要因为一个新网站而引入第二套采集或注册机制。

## Discover The Real Source

根据项目能力选择访问方式：

1. 优先使用项目已有的浏览器或 HTTP 客户端；
2. 动态页面使用 Playwright 或项目已有浏览器封装；
3. 监听或检查网络请求，识别页面实际使用的 JSON API；
4. 使用结构化 HTML、JSON 或 RSS 解析，不用脆弱的字符串截取；
5. 记录实际 URL、状态、等待条件、容器、字段和排序；
6. 区分目标内容与导航、广告、用户信息、项目卡片、历史内容及推荐内容；
7. 页面与接口不一致时，明确报告差异，不要猜测。

如果网站不可访问、需要登录、触发验证码或结构不足以确认需求，停留在探查阶段并说明阻塞原因。

## Preview Before Coding

试采集结果必须在修改代码前展示。按板块分组，每条至少显示标题和 URL，并说明：

- 访问的页面或接口；
- 实际采集方式；
- 每个板块采集数量与用户要求的差异；
- 是否有重复、混入或内容不一致；
- 当前无法确认的部分。

结尾使用明确的确认问题：

```text
以上试采集结果是否符合你的需求？
请明确回复“确认”或提供需要调整的内容。
在得到确认前，我不会修改业务代码，也不会实现解析器。
```

用户否定或修改后，重新完成完整探查和试采集展示，不要只描述改动方向。

## Source Type Branches

### Ordinary source

一个页面或接口对应一个解析器和一个结果键：

```text
source -> URL/API -> parser -> result key
```

只实现用户要求的单一采集逻辑，按需求截断条数并去重。

### Composite source

一个逻辑信息源包含多个需要独立返回的板块：

```text
source
├── section_a -> URL/API -> parser -> result_a
├── section_b -> URL/API -> parser -> result_b
└── section_c -> URL/API -> parser -> result_c
```

每个板块必须独立拥有页面/API、解析器实例、结果键、`source` 字段、数量限制和错误记录。
不要先合并成一个列表再用标题或位置推断来源。用户要求独立返回时，格式化也应生成独立消息。

## Implement

实现必须遵循当前项目的代码风格和边界：

- 继承既有解析器基类；
- 返回项目统一的数据模型；
- 标题和 URL 非空校验；
- URL 规范化和按 URL 去重；
- 使用 JSON 解析 API 响应；
- 不把当前采集到的标题、URL 或数量内容硬编码；
- 详情解析接口如项目已有约定则保留；
- 复合信息源分别注册 sections 或项目等价结构；
- 只有实际需要时才修改采集编排、formatter、模型和 README；
- 不做无关重构。

实现阶段开始前，应先简短说明拟修改的文件和板块映射。

## Verify

至少执行与项目匹配的以下检查：

```text
[ ] 解析器可导入或实例化
[ ] 信息源注册表包含目标标识
[ ] 普通/复合类型与用户输入一致
[ ] 结果键和 source 字段正确
[ ] 复合板块未合并
[ ] 数量限制正确
[ ] 标题、URL 非空且 URL 无重复
[ ] 真实网站链路验证通过
[ ] formatter 标题和消息边界正确
[ ] 语法检查通过
[ ] git diff --check 通过
```

优先用项目自己的客户端跑真实页面；不能访问时说明未完成真实验证及原因。没有自动化测试时要明确报告。

## Final Report

最终报告必须基于实际操作和代码结果，包含：

- 信息源标识及普通/复合类型；
- 访问的页面或 API、采集方式和各板块结果键；
- 实际修改、新增或删除的代码文件；
- 每个文件实现或维护的内容，以及对采集、格式化、接口、配置或文档的影响；
- 实际执行的验证、结果和证据；
- 未完成项、未执行验证及原因；
- 已知风险和需要用户关注的行为变化。

使用专业、简洁、完整的中文描述，不用提交标题或提交正文格式包装报告。没有未完成项或已知风险时明确写“无”，不要省略栏目。报告完成后停止本 Skill，不执行任何版本控制写操作。
